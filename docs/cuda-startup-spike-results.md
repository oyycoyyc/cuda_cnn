## 已确认线索（只读）

- 生产的设备准备阶段由 `cudaGetDeviceCount`、`cudaSetDevice(0)`、`cudaGetDeviceProperties(0)` 依次构成。
- `/etc/ld.so.preload` 含 Orion GPU 预加载库和 Libra 预加载库，其中 Libra 路径重复出现；没有修改或禁用。
- `/usr/lib/x86_64-linux-gnu/libcuda.so.1` 实际指向 `/opt/orion/orion_runtime/gpu/cuda/libcuda_orion.so`。
- 上述信息证明平台封装参与加载，不足以证明其是 1.4 秒开销的根因，也不能据此断定重复配置导致重复初始化。
- NVIDIA 文档说明 CUDA 12.0 起 `cudaSetDevice` 会初始化运行时和所选设备主上下文；不同 API 首次调用可能承担不同初始化工作，需要实测。

## 临时诊断方案

同一个源文件构建无 CUDA 引用的普通 C++ 空程序，以及默认链接 CUDA Runtime 的探针。探针包含无显式 CUDA 调用的空模式、各 API 单独先调用两次的模式，以及与生产一致的三 API 顺序再重复一次的模式。每个模式均以独立进程启动，多次交错运行，不预热后冒充首次执行。

API 时间用进程内单调时钟测量；总进程时间用外部单调时钟测量，包含启动和退出。两者之差同时包含加载、构造、退出清理和记录开销，不能全归为某一项。

生产顺序场景：首次 `cudaGetDeviceCount` 中位数 1149.152 ms，随后首次 `cudaSetDevice(0)` 为 159.857 ms，首次设备属性查询为 0.004713 ms；第二轮同 API 调用均低于 0.003 ms（中位数）。

所有原始慢样本均保留，没有丢弃。部分 CUDA 场景达到约 4 秒，表明环境存在明显波动。这些是 API 诊断，不是完整 MNIST 推理性能结果，也不能将第二次调用耗时作为启动成本。

已确认：耗时主要出现在首次显式 CUDA 调用／初始化路径，而不是单纯链接 CUDA Runtime 的空程序。直接把 `cudaSetDevice` 放到第一步仍有约 1.3 秒首次调用开销，不能据此认为跳过设备数量查询就能消除启动成本。尚未区分 CUDA 内部、原生驱动和平台封装各自的占比。
