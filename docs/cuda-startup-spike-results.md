## 已确认线索（只读）

- 生产的设备准备阶段由 `cudaGetDeviceCount`、`cudaSetDevice(0)`、`cudaGetDeviceProperties(0)` 依次构成。
- `/etc/ld.so.preload` 含 Orion GPU 预加载库和 Libra 预加载库，其中 Libra 路径重复出现；没有修改或禁用。
- `/usr/lib/x86_64-linux-gnu/libcuda.so.1` 实际指向 `/opt/orion/orion_runtime/gpu/cuda/libcuda_orion.so`。
- 上述信息证明平台封装参与加载，不足以证明其是 1.4 秒开销的根因，也不能据此断定重复配置导致重复初始化。
- NVIDIA 文档说明 CUDA 12.0 起 `cudaSetDevice` 会初始化运行时和所选设备主上下文；不同 API 首次调用可能承担不同初始化工作，需要实测。

## 临时诊断方案

同一个源文件构建无 CUDA 引用的普通 C++ 空程序，以及默认链接 CUDA Runtime 的探针。探针包含无显式 CUDA 调用的空模式、各 API 单独先调用两次的模式，以及与生产一致的三 API 顺序再重复一次的模式。每个模式均以独立进程启动，多次交错运行，不预热后冒充首次执行。

API 时间用进程内单调时钟测量；总进程时间用外部单调时钟测量，包含启动和退出。两者之差同时包含加载、构造、退出清理和记录开销，不能全归为某一项。

## 追加资源观察：只运行 4 个新进程

观察器 `diagnostics/observe_cuda_startup.py` 由子代理编写、主代理完整审查，使用 Linux `wait4` 取得完整子进程资源用量，约每 20 ms 只读采样该子进程的线程状态、等待点和调度计数。不使用 ptrace/perf，不安装工具，不改环境或平台配置。临时输出仅在诊断目录创建。先用 6 个普通进程用例验证正常退出、睡眠、CPU 工作、退出码 7、超时杀死与回收、大输出捕获，以及字段解析和临时文件关闭，再执行以下观察。

| 场景（各 1 次） | 观察周期 / ms | 子进程用户态 CPU / ms | 内核态 CPU / ms | wait4 最大 RSS / KiB |
|---|---:|---:|---:|---:|
| 普通 C++ 空程序 | 43.368 | 13.488 | 8.992 | 89340 |
| count-first | 1338.605 | 31.548 | 515.375 | 157720 |
| set-first | 1581.408 | 60.056 | 740.696 | 159696 |
| 生产 API 顺序 | 1641.401 | 45.307 | 774.348 | 159564 |

这些有采样扰动的时间不是新的性能验收结果。观察周期包含启动、退出、观察器准备及发现退出的延迟；`wait4` CPU 覆盖全部子线程与退出清理，不专属于首次 API。RSS 为整个 fork/exec 子进程生命周期的高水位，可能包含 exec 前继承的父进程内存，不能称为模型内存；采样到的最大 VmRSS 依次为 7640、119216、158552、151384 KiB，且可能漏掉瞬时峰值。

关键结果：

- 4 个子进程均退出 0、未超时；采样读取没有权限、解析或消失竞态错误。
- CUDA 场景的首次显式调用仍昂贵：count-first 为 1262.011 ms，set-first 为 1402.904 ms；生产顺序中 count 为 1233.485 ms、随后 set 为 213.707 ms，属性查询为 0.017 ms。
- CUDA 主线程同时有 CPU 活动和睡眠／不可中断等待。count-first 的 67 次主线程快照为 R=23、S=29、D=14、Z=1；set-first 为 R=31、S=27、D=13、Z=8；生产顺序为 R=41、S=29、D=11、Z=1。快照数量不是各状态的精确持续时间，R 也不等于正在 CPU 上执行。主线程成为 Z 时其他线程仍可能在清理，不能把它当作完整进程结束。
- 主线程等待点包括 `do_poll.constprop.0`、`os_acquire_rwlock_read`、`rwsem_down_write_slowpath`、`__wait_rcu_gp` 等；辅助线程还有 eventfd/futex 等等待。`wchan=0` 仅代表没有可用等待点，不能用于归属原生驱动或平台库。
- 采样区间内 CUDA 主线程累计运行队列等待增量仅为 0.403、0.149、0.619 ms；这是等 CPU 的时间，不含锁或 poll 睡眠。辅助线程的采样累计 CPU 很少，仅 set-first 退出附近另一个线程约 110 ms。可见线程数峰值分别为 5、6、6，未见数百个活跃初始化线程。
- 四次观察前后 cgroup 的 `nr_throttled` 与 `throttled_usec` **均无增长**；`cpu.max` 始终为 `200000 100000`，memory.events 的 high/max/oom/oom_kill 均为 0。组内计数包含观察器与其他同组进程，但本区间没有新增可见节流；现有证据**不支持将 2 核配额节流认定为此次 1 秒级开销的主要原因**。不排除不可见祖先限制或其他时刻负载变化。
- CUDA 子进程均记录 2219 次 major faults，但 `inblock=0`；仅凭缺页计数不能认定慢磁盘读取是根因。

因此，不能将全部启动延迟解释为“CPU 不够”或单纯 CPU 计算：既有 515–774 ms 内核态 CPU 工作，也有明显轮询／锁等待。仍不能把各项归因到具体平台封装或原生驱动，未尝试绕过封装。

## 对最新 100 ms 目标的影响

降低准确率要求不会自动消除首次 CUDA 初始化。当前平台上，保持每次独立启动并调用 CUDA 的方案尚无达到 100 ms 的证据；仅优化后续算子不足以填平差距。
